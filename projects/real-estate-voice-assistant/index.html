01 / The problem

The caller rarely has every detail.

The idea came from the everyday workflow of a real-estate office. People call after seeing a listing on Sahibinden or a phone number on a physical banner. Some know the listing ID. Others remember only that it was a rental apartment.

The useful task is to collect the clues they actually have, identify a listing when there is enough evidence, and prepare callback details. A caller who does not know the district or consultant should not get stuck answering the same question.

A / LISTING NUMBERA Sahibinden ID is available.

Normalize the stated number and use an exact lookup. Ask the caller to confirm the matching record.

B / CONSULTANTThe caller remembers a name.

Restrict the search to that consultant’s records. One consultant may represent several properties, so the name alone may not identify the listing.

C / PARTIAL CLUESThe banner is all they remember.

Use location, rent/sale, property type, rooms, floor or surroundings to rank candidates. Ask for useful missing evidence, and allow the result to remain unresolved.

02 / How it works

From speech to a useful next step.

The current input is a browser microphone. A text test panel exercises the same extraction, dialogue and portfolio flow without speech recognition.

  1. 01 / LISTEN

    Find the speech boundary.

    Silero VAD detects speech and pauses in the audio stream. A completed utterance goes to whisper.cpp for Turkish transcription.

  2. 02 / EXTRACT

    Turn words into fields.

    Qwen returns structured listing clues: source, number, consultant, location, property type, room layout, floor and explicitly unknown information.

  3. 03 / REMEMBER

    Keep context across turns.

    The application merges new facts with earlier answers. It tracks unavailable information and previously asked topics in temporary browser state.

  4. 04 / SEARCH

    Rank the possible properties.

    A separate FastAPI service searches fictional JSON listings. Exact IDs take priority; field matches and contradictions contribute to explainable candidate scores.

  5. 05 / CLARIFY

    Ask about a difference.

    Candidate field distributions constrain the next question. Qwen chooses an eligible field; application checks reject forbidden choices. No useful question is a valid outcome.

  6. 06 / CONFIRM

    Check the match.

    The caller confirms or rejects a proposed listing. The demo can collect a temporary callback summary and optionally speak its reply with FreyaTTS-small.

The next question depends on the remaining candidates. If all candidates are apartments for rent, asking “Was it for rent?” adds little. A floor or room-layout question may help—unless the caller has already said they do not know.

03 / Engineering decisions

Bound the model’s responsibilities.

Local inference, separate components.

I chose local speech and language models to explore an office-controlled installation and avoid making the prototype depend on hosted inference for every turn. Speech recognition, the LLM, search and speech synthesis run as separate processes.

Trade-off: local execution moves the compute and maintenance burden onto the installation machine. Hardware support and response time need measurement.

Use application code for facts and rules.

The LLM interprets language; application code performs lookups, maintains state and checks eligible question fields. Listing IDs use exact matching. Candidate scores have visible field contributions rather than an unexplained model confidence value.

Trade-off: the scoring weights are initial heuristics. Similar properties, incorrect transcriptions and conflicting clues can still lead to a poor ranking.

Treat “I don’t know” as information.

A missing answer and an unavailable answer are different states. Unknown fields should constrain future questions. The application validates a structured field identifier alongside the model’s question, with a rule-based fallback if generation fails.

Trade-off: wording, state updates and fallback paths must follow the same policy. Repeating an unavailable question was a concrete failure mode uncovered during development.

Start with sample records.

Fictional listings make candidate scores and dialogue mistakes easier to inspect before connecting a real office database. This prototype uses structured lookup and scoring; PostgreSQL, pgvector and RAG are planned extensions.

Trade-off: success against a small sample portfolio does not establish accuracy with real listings or real callers.

05 / Evidence & restrictions

What the prototype proves—and what is still open.

What I have checked

An initial text-only evaluation covered 20 scenarios: 15 passed, 4 failed and 1 was partial. Several failures involved extracting an explicitly stated location or consultant. That report is an early baseline, not a current accuracy claim.

The packaged repository also has 18 lightweight Python and JavaScript checks covering installer behavior and dialogue guards. They use fixtures and mocked services; they do not measure real model or speech quality.

Read the initial evaluation ↗

Current restrictions

  • Input is a browser microphone, not a real telephone call.
  • Listings are fictional; there is no production office database or implemented RAG pipeline.
  • Callback details are temporary browser state. No consultant or WhatsApp notification is sent.
  • End-to-end audio is not fully streaming. Local response time has been slow in testing; a new stage-by-stage benchmark is still needed.
  • Some callers simply lack enough identifying information. The system must handle that without inventing a match.

Next iteration: evaluate multi-turn conversations with repeated unknown answers, corrections and rejected candidates; measure each audio/model stage; then connect durable office data and a real call/notification workflow separately.

06 / Native installation

Keep the source small. Fetch the models.

The public repository contains application code, fictional data, tests and a native macOS installer. Model weights, third-party source, Python environments and builds are downloaded into an ignored local directory.

The installer records upstream revisions and verifies model downloads by size and SHA-256. It supports CPU and Apple Silicon Metal profiles; TTS is optional, with CPU and an MPS option to evaluate.

This demonstrates a local deployment approach for an office-controlled installation. First setup needs internet access and several GB of storage; inference uses installed local assets.

A full first-time installation and audio session on a clean Mac have not yet been verified end to end. Linux, Windows and unattended office deployment have not been validated.
